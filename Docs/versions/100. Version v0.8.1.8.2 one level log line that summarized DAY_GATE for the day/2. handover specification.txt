Handover Specification
Transition from Midas_V2 v0.8.1.8.2 → v0.8.1.9.0
(Standardized on scripts/run_range_and_summarize.py + log capture for all A/B testing)
1. Purpose of This Handover

This document transfers complete context, constraints, and next-step intent from v0.8.1.8.2 into the next version (v0.8.1.9.0), ensuring:

v0.8.1.9.0 introduces exactly one profit-affecting change

That change is validated via extensive A/B testing over a wide date range

All profit claims are measurable, explainable, and reversible

No diagnostic/safety foundations are weakened

Testing is standardized and logs are captured so results can be compared cleanly

This is not a release note and not a Copilot spec. It defines what must be preserved, what may change, and how success is judged.

2. Authoritative State at End of v0.8.1.8.2
2.1 Execution & Stability

Backtester executes end-to-end without crashes.

Runtime stability fix is in place:

Safe fallback for missing post_entry_expansion_gate (must remain).

2.2 Observability (Major Milestone)

v0.8.1.8.2 introduced day-level observability:

Exactly one DAY_GATE_SUMMARY log per successfully executed day.

Emitted after DAY_GATE evaluation and after structural-damage auto-switch finalization.

Enables deterministic day classification using close_gt_vwap_cnt.

2.3 Trading Behavior

Trading behavior remains identical to v0.8.1.8.1:

No changes to entry logic, exits, sizing, indicators, or PnL computation.

v0.8.1.8.2 added observability only (plus stability fixes discovered during validation).

3. What v0.8.1.8.2 Proved (Key Findings)
3.1 DAY_GATE is functioning correctly

Zero-trade days are policy-driven, not bugs.

3.2 Day regimes are now explicit

Using close_gt_vwap_cnt:

close_gt_vwap_cnt	Regime	Current behavior
0	Hostile	Trade 0
1	Marginal	Trade 0
≥2	Healthy	Trade normally
3.3 Marginal days are structurally different

Empirical observation from July:

close_gt_vwap_cnt == 1 days are not equivalent to hostile days.

They often contain one legitimate continuation opportunity.

Current binary gating suppresses them entirely.

This is the first high-confidence profit lever.

7. Locked Direction for v0.8.1.9.0
7.1 Agreed policy change
Day regime	Behavior in v0.8.1.9.0
Hostile (cnt==0)	Trade 0 (unchanged)
Marginal (cnt==1)	Allow exactly 1 trade (first valid signal)
Healthy (cnt>=2)	Unchanged
7.2 Trade selection rule

The first valid signal of the day

No ranking, no scoring, no waiting

Deterministic and reversible.

8. Mandatory A/B Testing Requirement (Critical)
8.1 Why wide-range A/B testing is mandatory

This change loosens a gate; small losses can accumulate silently. A single good day proves possibility, not profitability. Therefore, extensive A/B is required.

8.2 A/B definition (must be identical symbol/date sets)

Variant A (control): v0.8.1.8.2 — marginal days trade 0

Variant B (treatment): v0.8.1.9.0 — marginal days trade max 1

Everything else identical.

8.3 Metrics (must compare all)

Net PnL

Profit factor

Win rate on marginal-day trades

Max drawdown

Average loss size

Loss clustering / streakiness

Profit improvement with materially worse drawdown is not acceptable.

8.4 Success criteria (minimum)

Meaningful net profit improvement across the full range

Drawdown does not materially worsen

Healthy-day results unchanged

Hostile days remain suppressed

Marginal-day trades show non-destructive expectancy (preferably positive)

11. Handover Summary (One Paragraph)

v0.8.1.8.2 completed the diagnostic phase by making day-level trade suppression explicit and by stabilizing runtime execution, establishing a reliable baseline for profit work. The system now clearly distinguishes hostile, marginal, and healthy days using the existing DAY_GATE counter close_gt_vwap_cnt. v0.8.1.9.0 will introduce exactly one profit-affecting change: allow exactly one trade on marginal days (close_gt_vwap_cnt==1) while leaving hostile-day suppression and healthy-day behavior unchanged. This must be validated via extensive A/B testing using the standardized range runner (run_range_and_summarize.py) with outputs captured to log files so Variant A (v0.8.1.8.2) can be compared directly to Variant B (v0.8.1.9.0) across wide date ranges.
