Phase 1 – Build the DB spine and ingestion

Goal: Every completed trade and its entry/exit indicators end up in a small, clean set of tables (even SQLite is fine at first).

Tables to start with:

trades – one row per trade (the “spine”)

snapshots – entry/exit indicators per trade

(Optional later: candles_1m, candles_1s, runs)

Ingestion script (Python, Copilot-driven when you’re ready):

Read each results CSV + TWCS JSONs

Join on trade_id

Insert into trades and snapshots

Tag each row with:

Date range / run label

Midas version (e.g. v0.8.1.0.5)

Scenario name (B, D_strict, etc.)

That gives you a history like:

“Scenario B, v0.8.1.0.5, Aug 5–31, every trade and its indicators.”

Phase 2 – Run descriptive analysis (no changes yet)

Here we look first, don’t touch rules yet.

For a set of runs (say August 2025, Scenario B), you ask:

Basic stats:

Win rate, avg PnL, expectancy (R), PF, # trades.

Indicator distributions at entry:

Histogram of macd_hist, macd_slope, vwap_slope_bps, green_streak, rvol_open.

Compare winners vs losers:

e.g. median vwap_slope_bps for winners vs losers.

Most important: conditional splits:

“WR / expectancy when green_streak >= 3 vs < 3.”

“WR when vwap_slope_bps > 0 vs <= 0.”

“WR when macd_hist > 0 and macd_slope > 0 vs all others.”

“WR when rvol_open >= 2.0 vs < 2.0.”

“WR by gap band (10–20 / 20–30 / 30–40).”

You’re just measuring. No rules changed yet.

Phase 3 – Identify failure patterns worth testing

Now you scan those splits for “obvious uglies,” like:

“Trades where vwap_slope_bps <= 0 at entry have WR 30% and -0.3R expectancy.”

“Trades where green_streak < 3 are breakeven or negative.”

“Trades where macd_slope < 0 at entry are strongly negative.”

“Trades where rvol_open < 1.5 have terrible follow-through.”

You turn these observations into candidate rules:

Candidate Gate 1: Require vwap_slope_bps > 0 at entry.

Candidate Gate 2: Require green_streak >= 3.

Candidate Gate 3: Require macd_hist > 0 AND macd_slope > 0.

Candidate Gate 4: Require rvol_open >= 1.5 in the first N minutes.

You don’t assume they’ll all help; they’re just hypotheses.

Phase 4 – Turn each hypothesis into a parameter / flag

For each candidate rule, you:

Add a config flag (in JSON) like:

"require_positive_vwap_slope": true

"min_entry_vwap_slope_bps": 0

"min_entry_green_streak": 3

"require_positive_macd_slope": true

"min_rvol_open": 1.5 (you already have this concept)

Wire it into the strategy via Copilot:

In should_enter, add checks that consult these flags.

Make sure old behavior = “flags off”.

Keep each change tiny and toggle-able so we can A/B cleanly.

This matches your existing discipline: config-first, code later, always safe defaults.

Phase 5 – A/B backtest each candidate rule

This is where your “measurable profitability workflow” kicks in.

For a given candidate rule:

Choose a date range (e.g. Aug 5–31, Scenario B).

Run baseline: rule OFF (current best config). Save metrics.

Run experiment: rule ON. Same dates, same universe builder.

Then compare:

Win rate (WR)

Expectancy / avg PnL per trade (R)

Profit factor

Total PnL

of trades (did we cut too many?)

Per your own criteria (stored in memory):

keep it only if it gives ≥ +3 percentage points WR or +0.2R expectancy or similar, with sensible trade count.

If it fails → rule is rejected or tweaked and re-tested.

This makes the DB → rules flow scientific, not “feels right.”

Phase 6 – Promote successful rules to the baseline

When a rule clearly helps:

Fold it into the baseline scenario config (e.g. Scenario B).

Tag a new version (v0.8.1.X) after:

validating multiple months (Aug + Sep, etc.)

updating docs (DEV_GUIDE, commands, summary).

Now:

Scenario B is a better, data-driven version.

You’ve locked in real profitability improvement, not a hunch.

Phase 7 – Use the same loop for adaptive sizing

Once the entry gating is solid, you can use the same DB to:

Classify trades into “quality buckets” based on indicators:

High quality: strong VWAP slope, MACD rising, high RVOL, big green streak.

Medium quality: mixed signals.

Low quality: borderline conditions.

Measure expectancy of each bucket:

If high-quality bucket has much higher PnL and WR:

Map it to higher risk_usd in your sizing module.

If low-quality trades are barely profitable or negative:

Reduce risk or kill them.

Again: all A/B tested, versioned, and documented.

Phase 8 – Close the loop with PNGs and UI

Finally, you marry:

DB analysis (numbers)

PNG snapshots (visuals)

Local UI (Claude-driven panels)
