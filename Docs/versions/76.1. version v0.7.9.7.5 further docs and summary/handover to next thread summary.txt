These settings control when and how we are allowed to enter a trade

2.2.1 Timing and volume gates

gate_minutes: 20

We wait 20 minutes after the open before any entries.

Purpose: avoid early open chaos.

min_pm_vol: 30,000

Before the market opens, the stock must have traded at least
30,000 shares premarket.

Purpose: avoid completely sleepy symbols.

min_rvol_open: 2.0

rvol_open_minutes: 15

In the first 15 minutes, today’s volume must be at least
2.0× yesterday’s volume over the same number of minutes.

Purpose: ensure the stock is unusually active today, not just
a quiet name with a random gap.

2.2.2 Green candle (“green streak”) rule

Implemented via _passes_price_rise_gate(bars, i) in strategy.py.

rise_bars: 3

green_body_min: 0.22

Exact meaning:

We require 3 recent green candles in a row.
For each of those candles:

The close must be higher than the previous candle’s close, and

The candle’s body must be at least 22% of the full bar range
(no tiny doji candles).

If any one of those 3 bars fails (not green, not strong enough body),
no entry.

This is your implemented green streak rule.

2.2.3 MACD histogram rule

Implemented via _passes_macd_gate(closes, i) in strategy.py.

require_macd_rise: True

macd_rise_bars: 2

Exact meaning:

The MACD histogram must be:

Above zero (bullish momentum), and

Rising for 2 bars in a row
(current histogram > previous histogram, twice).

If this condition fails, no entry, even if green candles and volume
conditions are satisfied.

2.2.4 Take profit and stop loss

tp_pct: 2.0

Take profit at +2.0% above entry price.

sl_pct: 2.5

Stop loss at –2.5% below entry price.

These define the reward/risk of each trade in this version.

2.2.5 Dip reclaim mode (OFF here)

dip_reclaim: False

Dip-reclaim logic is present in strategy.py but is disabled
(dip_reclaim=False) for Scenario B in this branch. Basic breakout
mode is used.

Where these live today:

strategy.py → StrategyParams dataclass.

This section is to remind the assistant (and you) how this project is structured and how we change code safely.

ChatGPT (this model)

Acts as designer / architect / spec-writer.

Produces:

Human-readable explanations of logic and behavior.

Pseudocode and precise specifications for changes.

Detailed prompts/instructions for Copilot (Python/backend) and for Claude (website/frontend).

GitHub Copilot (inside Visual Studio / VS Code)

Is the Python code editor/writer.

You open a file (e.g., backtester.py, strategy.py, topgappers.py) and paste in the spec from ChatGPT.

Copilot generates or modifies the Python code.

You never hand-edit Python (as much as possible); Copilot does the diff, you review and accept.

Claude (via website) for the local website / React UI

Is the TypeScript/TSX code writer for the local runner UI (MidasLocalRunnerUI.tsx, etc.).

For UI work:

ChatGPT writes a design spec for the frontend.

You paste that spec into Claude.

Claude generates/edits the React/TSX code.

You do not manually type the TSX; Claude does, you review.

You (Malcolm)

Glue, orchestrator, and tester.

Responsibilities:

Decide version boundaries (v0.7.9.7.5, v0.7.9.7.6, etc.).

Paste ChatGPT specs into Copilot (backend) or Claude (frontend).

Run tests (run_range_and_summarize.py, etc.).

Observe outputs and logs.

Save Atlas and version docs in Docs/.

3.2 Backend change process (Python / Copilot)

When we need to change Python (scanner, strategy, backtester, risk), the process is:

Design phase (ChatGPT):

You describe what you want (“move scanner knobs into JSON”, “add new summary line”, “change risk wording”).

ChatGPT reads relevant files / logs and:

Explains current behavior.

Proposes a very clear, step-by-step spec:

What functions to modify.

What fields to add or read.

What new text should look like.

ChatGPT provides a Copilot spec block, usually starting with START and ending with END.

Implementation phase (Copilot):

You open Visual Studio / VS Code with the relevant file (backtester.py, strategy.py, topgappers.py).

Open Copilot chat or inline prompt.

Paste the exact spec from ChatGPT (between START and END) into Copilot.

Copilot proposes code changes (diff).

You review the diff. If it looks correct, you accept and save.

Testing phase (you):

Run a known test command, for example:

python scripts\run_range_and_summarize.py --start 2025-08-01 --end 2025-08-02 --scenario B


Check:

Does the output still match the Atlas (if behavior should be unchanged)?

Are summaries correct and clear?

If something is wrong, you bring the output back to ChatGPT and we adjust the spec.

Documentation phase:

After a stable change, you update:

The Atlas (if behavior changed intentionally).

The version summary (e.g., Docs/PARAMETER_ATLAS_ScenarioB_v0.7.9.7.6.md and a short version log).

We do not edit Python directly by hand, to keep changes aligned with the design and reproducible.

3.3 Frontend change process (React UI / Claude)

For the local website / UI (e.g. MidasLocalRunnerUI.tsx):

Design phase (ChatGPT):

You explain what you want the UI to do (e.g., show new parameters, allow editing top, show rise_bars read-only, etc.).

ChatGPT writes a UI design spec:

What new fields to show.

Whether they’re editable or read-only.

How they map to JSON fields.

Which backend endpoints to call (e.g., patch server at 127.0.0.1:5001).

Implementation phase (Claude):

You paste that UI spec into Claude (on Claude’s website).

Claude generates / updates the TSX (MidasLocalRunnerUI.tsx or related files).

You copy the generated TSX back into your midas-ui project.

Testing phase:

Run npm run dev for the UI.

Visit the local UI (e.g., http://127.0.0.1:5173) and:

Check that the new controls appear.

Check they send correct JSON to the patch server.

Confirm they don’t crash.

Again, you do not hand-edit TSX unless absolutely necessary; Claude is the code generator for that side.

3.4 Versioning and testing discipline

For each version (e.g., v0.7.9.7.5, v0.7.9.7.6):

Define the scope clearly (like we’re doing now: v0.7.9.7.6 = config unification, no DB/candles).

Apply small changes with Copilot / Claude, always backed by:

A spec from ChatGPT.

A test command with known outputs (e.g., Aug-01 Scenario B).

Run tests after each small change, not just at the end.

Update docs (Atlas and version summary) once the version is stable.

Only then, start a new thread for the next version, pasting:

A version handover packet.

The relevant Atlas.

This keeps your project testable, understandable, and profitable.
