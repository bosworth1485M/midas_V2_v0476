1. Purpose of v0.8.1.14.0

v0.8.1.14.0 does NOT change trading logic.

Its purpose is to systematically analyze the new blocked-trade JSON snapshots introduced in v0.8.1.13.0 and determine, with evidence:

Which guards are preventing losses

Which guards may be blocking profitable trades

Under what conditions (day quality, continuation strength, structural context)

Only after this analysis will we justify one narrowly scoped, profit-oriented structural change.

This version is still diagnostics + analysis, not strategy modification.

2. New Data Available (What Changed in v0.8.1.13.0)

For each blocked trade candidate (for instrumented guards), we now have a persistent JSON snapshot containing:

date, time, symbol

scenario

day classification (hostile | marginal | healthy)

block reason

continuation strength (count)

structural context

guard enablement state

This data did not previously exist in structured form.

3. Canonical Data Location

Blocked-trade snapshots live at:

out\<YYYYMMDD>\B\blocked_candidates\


Example:

out\20251104\B\blocked_candidates\POST_DAMAGE_CONTINUATION_BLOCK_IHRT_1031.json


Each file represents one blocked trade opportunity for the instrumented guard.

4. ⚠️ Important Clarification: Meaning of blocked_candidates and Warnings

The directory name blocked_candidates must not be interpreted literally.

What blocked_candidates DOES mean

In v0.8.1.13.0:

It contains snapshots only for guards that have been explicitly instrumented

Currently, only one guard is instrumented:

POST_DAMAGE_CONTINUATION_BLOCK

Each JSON represents:

A trade opportunity blocked by the post-damage continuation guard, captured for diagnostics.

What it DOES NOT mean

The following interpretations are incorrect:

❌ “All blocked trades are listed here”

❌ “No directory means no trades were blocked”

❌ “Few files means the system rarely blocks trades”

Many other guards may block trades (DAY_GATE, VWAP_EXT, MAX_TRADES, DAILY_MAX_LOSS, etc.), but they are not instrumented yet and therefore do not write JSON snapshots.

Relationship to warning logs

A warning like:

[WHY] POST_DAMAGE_CONTINUATION_BLOCK ...


means the guard fired.
A JSON snapshot exists only if:

the guard fired,

the snapshot write succeeded,

and this was the first occurrence for that symbol/day (log-once latch).

Why this limitation is intentional

This partial instrumentation is deliberate:

Focus on one loss class at a time

Avoid noisy or misleading datasets

Keep conclusions scoped and honest

Correct interpretation rule:

Absence of files means only that the instrumented guard did not fire — nothing more.

8. Valid vs Invalid Conclusions
Valid conclusions

“On healthy days, count=1 often still fails”

“On healthy days, count=1 often leads to later continuation”

“On marginal days, continuation is unreliable”

Invalid conclusions

“One blocked trade would have won”

“We should loosen the rule everywhere”

“The guard is bad because it blocked a winner”

Single examples are not sufficient.

9. How This Leads to Better Results

This version enables loss subtraction with evidence.

avoid overfitting to hostile regimes

preserve performance in marginal regimes

Profit comes from the next version, not this one.
