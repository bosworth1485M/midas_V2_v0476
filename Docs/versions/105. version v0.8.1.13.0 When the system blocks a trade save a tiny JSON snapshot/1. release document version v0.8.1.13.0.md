Version v0.8.1.13.0 — Diagnostics-Only Blocked-Trade Snapshotting
Purpose of This Version

The purpose of v0.8.1.13.0 is to add non-intrusive observability to a specific, already-validated structural guard, without changing any trading behavior.

This version introduces a tiny JSON snapshot that is written only when a specific trade is blocked, capturing why it was blocked in a structured, persistent form.
No strategy logic, thresholds, control flow, or configuration values were changed.

This version is explicitly diagnostics-only.

Background and Motivation

Prior to this version, when a trade was blocked by a structural guard such as:

POST_DAMAGE_CONTINUATION_BLOCK


…the only record of that decision was a transient log line.

Logs alone are insufficient because:

They are unstructured and difficult to aggregate

They do not preserve contextual state (day classification, auto-mode state, etc.)

They disappear once the log scrolls or is rotated

They do not allow systematic review of blocked trade opportunities

As a result, when trading performance is poor, it is impossible to know whether:

Guards are successfully preventing losses, or

Guards are incorrectly blocking profitable trades

v0.8.1.13.0 closes this observability gap without altering behavior.

What This Version Does (Exactly)
1. Instruments a Single, Specific Guard

This version adds snapshotting only for:

Guard: Post-Damage VWAP Reclaim Continuation Guard

Condition:

green_above_vwap_count < 2


Existing log anchor (unchanged):

[WHY] v0.8.1.12.0 POST_DAMAGE_CONTINUATION_BLOCK


No other guards are instrumented in this version.

2. Snapshot Is Written Only on the Log-Once Path

The snapshot is written only when the guard fires for the first time per symbol/day, matching the existing early_reject_logged latch.

This guarantees:

One snapshot per blocked candidate

No duplicate files

No file spam

No performance impact

If the guard never fires on a run/day, no directory and no file are created.

3. Snapshot Writing Is Best-Effort and Non-Blocking

The snapshot write is wrapped in a silent try/except block.

If any error occurs (filesystem, permissions, encoding, etc.):

The error is swallowed

Trading logic proceeds unchanged

No logs are altered

No trades are affected

This preserves the invariant:

Trading behavior must never depend on diagnostics.

Output Location and Naming

When the block fires, the following directory is created:

out\<YYYYMMDD>\B\blocked_candidates\


Within it, a JSON file is written:

POST_DAMAGE_CONTINUATION_BLOCK_<SYMBOL>_<TS>.json


Example:

POST_DAMAGE_CONTINUATION_BLOCK_IHRT_1031.json


The directory exists only if at least one such block occurred.

Snapshot Contents

Each snapshot is intentionally small, deterministic, and structured.
No candles, TWCS data, or indicator arrays are included.

Example snapshot (verbatim)
{
  "auto_struct_damage": true,
  "count": 1,
  "date": "2025-11-04",
  "day_class": "healthy",
  "i": 61,
  "reason": "POST_DAMAGE_CONTINUATION_BLOCK",
  "recent_structural_damage": true,
  "recovery_passed": true,
  "reject_reclaim_effective": true,
  "scenario": "B",
  "symbol": "IHRT",
  "ts": "10:31",
  "version": "v0.8.1.13.0",
  "window": "i-1,i-2,i-3"
}


This captures why the trade was blocked, not just that it was blocked.

What This Version Explicitly Does Not Do

v0.8.1.13.0 does not:

Change any trading logic

Change any thresholds

Change any configuration values

Add or remove guards

Alter logs

Add TWCS graphics

Aggregate or analyze snapshots

Affect PnL in any way

It is pure instrumentation.

Why This Matters for Improving Results

This version does not improve profitability directly.

Instead, it enables:

Objective review of blocked trades

Separation of “good blocks” vs “bad blocks”

Guard refinement based on evidence

Loss subtraction without guesswork

It is a measurement instrument, not a strategy change.
